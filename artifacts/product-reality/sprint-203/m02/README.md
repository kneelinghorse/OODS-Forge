# s203-m02 — Objects born from CMOS's own record

Builder self-certified: **false**. Built on `codex/sprint-203-objects-and-context` from `3aff47115`
(m01 closed). Every shape was read from the live store with `sqlite3 -readonly`; **nothing was written
to CMOS**, and Forge gained no code path to it.

## The store, as it actually is (2026-09-16)

`cmos/db/cmos.sqlite`: **1,933** `strategic_decisions`, **186** `sprints`, **499** `sessions`,
**1,082** `missions`. The four tables carry more than the memo listed — every one also carries an
event-sourcing envelope (`stable_event_id`, `occurred_at`, `origin_seq`, `event_type`,
`schema_version`, `author_user_id`) that is CMOS's replication mechanism rather than the thing itself.

## The fit read comes first

[`fit-read.json`](fit-read.json), regenerated by [`fit-read.mjs`](fit-read.mjs), maps **every column of
all four tables** to a reused object, a reused trait, a new trait, a born field, or "not modelled"
with the reason, beside the null and distinct counts it was read from. The script fails its own output
if any column is left without a disposition — it caught six of mine on the first run.

| Table | born | reused trait | new trait | not modelled |
| --- | --- | --- | --- | --- |
| `strategic_decisions` (23 columns) | 8 | 2 | 2 | 11 |
| `sprints` (15 columns) | 3 | 4 | — | 8 |
| `sessions` (20 columns) | 7 | 5 | — | 8 |

What the fit read found that changes the design, rather than confirming it:

- **Several declared columns are dead in the live store.** `strategic_decisions.last_reviewed_at` and
  `author_user_id` are null on all 1,933 rows; `sessions.user_id` and `author_user_id` on all 499;
  `context_id` holds one value (`master_context`) on every row. None are modelled — a screen cannot
  show a field that has never been written.
- **CMOS's own mission counters are not usable.** `sprints.total_missions` is null on 176 of 186 rows
  and `completed_missions` on 177, so `Sprint` counts from the missions table instead of rendering a
  counter that is blank 95% of the time.
- **The links are sound.** Every non-null `sprint_id` resolves: 1,785 from decisions, 1,082 from
  missions, 301 from sessions, **0 dangling**. `mission_id` on a decision is not: it is often a bare
  `m02` rather than `s203-m02`, so it is shown as a label and never as a resolved link.
- **The long-free-text risk is quantified, not anticipated.** `decision_text` runs from 61 to **8,418**
  characters, mean 899, with **197 of 1,933 rows over 2,000**. `Sprint.focus` and `Session.summary`
  are present on every row and are free text too.

## The reuse is refused, on measurement

[`reuse-proof.json`](reuse-proof.json), from [`reuse-proof.mjs`](reuse-proof.mjs). The memo assumed
"CMOS's mission is largely a subset of the existing `research/Mission`", so the first move was to
prove it. It does not hold, on four independent counts:

| Blocker | Measured |
| --- | --- |
| Status vocabulary | CMOS writes Completed, **Dropped**, **Deferred**, In Progress, Queued. `Dropped` and `Deferred` have no counterpart in the research state set at all; the other three differ in case and spacing, and the object's own field description forbids coercing an unknown server value. |
| Identity type | `research/Mission.id` is `uuid` with `format: uuid`. **0 of 1,082** CMOS mission ids are uuid-shaped; they are slugs such as `s203-m06`. |
| Project identity | `project_id` is declared `uuid`; CMOS's are slugs (`forge`, `oods-foundry-mcp`). |
| Required fields | `materialization_pending` and `search_ready` are required TraceLab pipeline internals a CMOS mission has no value for. |

Beyond those, **41 of the object's 53 fields** are TraceLab plumbing that would render empty on a CMOS
mission screen, and three CMOS columns have nowhere to go — including `sprint_id`, the link that
organises the whole of CMOS. The object is also TraceLab-owned (`metadata.owners: TraceLab`) and its
README states the YAML "does not add columns to TraceLab", so widening it would edit another team's
contract; and the registry is keyed by object name, so a second `Mission` could not exist beside it.

**What was authored instead:** nothing named Mission. No screen in this sprint needs a standalone CMOS
mission, and one reaches these screens as `Sprint.mission_count` and as the `mission_id` a Decision
names. The three objects the memo names are what landed.

## What landed

`objects/delivery/` — **Decision**, **Sprint**, **Session** (alpha), with
[their README](../../../../objects/delivery/README.md) stating each divergence and its reason, in the
shape `objects/research/README.md` set.

`traits/lifecycle/Supersedable.trait.yaml` — the one genuinely new trait, with its parameter schema at
`schemas/traits/supersedable.parameters.schema.json`.

Supersession is a self-referencing lineage, not a workflow: a record is replaced by a later record and
both stay readable, which is why it is its own trait rather than a `Stateful` state set. Its field is
**`supersession_status`, not `status`**, so an object can carry a lifecycle through `Stateful` and a
supersession through this trait without the two colliding — `Stateful` owns `status` and is the
most-composed trait in the system.

**It serves both stores that already hold the shape, and they record it from opposite ends.** CMOS
writes the forward pointer (`superseded_by`, populated on exactly the 45 rows whose status is
`superseded` — a clean 1:1) beside a four-state vocabulary. Forge's own composition acceptances
(`CompositionAcceptance.supersedes: { version, acceptedAt } | null`) write the backward pointer and
leave the standing acceptance implicit. The trait declares both pointers and a `recordedDirection`
parameter naming which one the source of truth actually writes; the other is derived only where a
store can derive it and is otherwise absent, because an absent pointer means unknown, never "nothing
was superseded". `delivery.spec.ts` holds that mapping against both stores' real shapes.

Forge's acceptance record is **not** rewritten this sprint: it is read by the preview page, compare and
accept paths, and its schema belongs to m05. The trait covers it; adopting it there is not m02's to do.

## Two producer defects found by authoring from the real record

Neither was a defect in the objects — both are Forge's, surfaced because an object born from a live
store is shaped differently from one written to fit the tool:

1. **The Stack contract had fallen behind the composer.** `Sprint` is the **first object in the registry
   with both a `start_date` and an `end_date`**, so it composed a `DateRange` pattern group — and
   `target-contracts.ts` admitted only `patternComponent: 'StatusTimeline'`, so generation refused the
   screen (OODS-V007) in both frameworks. The composer can emit **eight** composite components. Fixed at
   the producer, and fixed so it cannot drift again: `field-patterns.ts` now exports
   `PATTERN_COMPOSITE_COMPONENTS`, derived from the pattern rules themselves, and the Stack contract
   reads that list instead of restating one value. The per-field existence check, which also applied to
   `StatusTimeline` alone, now applies to every pattern group.
2. **A `Badge` authored with a field directive is refused.** The canonical `Badge` contract has no
   `statusField` prop, so the trait's first view extension produced OODS-V007 on Decision's card and
   list. `StatusBadge` carries the directive and lowers it to the bound status; the trait uses it.
   (`traits/visual/Statusable.trait.yaml` authors `Badge` with `statusField` the same way and is
   composed by no object, so the same defect sits there unexercised — recorded, not fixed here.)

A third finding is left to m04 by name: **the composer's detail placement drops optional fields**, so
the supersession pointers — the whole point of the trait — never reached the detail screen. The trait's
own `view_extensions.detail` now surfaces them, which is the designed lever; the general placement
budget is not m02's to change.
