How Forge Works

Forge is a design system stored as definitions and operated through tools. You describe things (objects) as bundles of capabilities (traits); Forge assembles them into screens per context, styles them with tokens under a brand, and exports screens, code, charts and theme files — checking its own output as it goes. This page explains each piece, what it actually contains, and what you can do with it.

01The pieces, in one picture

defineTraitsReusable capabilities: fields + settings + UI pieces per screen + tokens.
defineObjectsThings you model (User, Product, Invoice…) = a list of traits + a few own fields.
assembleContextsList, detail, form, timeline, card, inline (+ chart, dashboard shells) — built from the traits' contributions.
styleTokens & brandsEvery colour/size/type value once; compiled to CSS, TS, Tailwind, Swift, Kotlin; switched by brand + theme.
export + checkTools24 registered tools (19 auto + 5 on demand), as defined by packages/mcp-server/src/tools/registry.json: compose, validate, render, code, charts, dashboards, certify, tokens, catalog.

Everything lives in one repository as plain files: traits and objects are YAML (traits/, objects/, domains/), tokens are JSON (packages/tokens/src/tokens/), components are packaged for React and Vue (packages/components-react/, packages/components-vue/) with shared styles (packages/component-styles/), and the tools are a local server (packages/mcp-server/). A tool is a typed function — name plus JSON in, JSON out — that you call over the Model Context Protocol from an AI assistant, over HTTP from a panel, or from the command line. Nothing requires a hosted service.

02Traits — what one is, what it contains

Trait

A single YAML file describing one capability an object can have — "has a lifecycle", "can be priced", "can be searched". The file carries everything that capability needs so that adding the trait to an object adds its data, its UI and its styling in one step.

A trait file has a named header (trait:). Across the authored inventory, its 11 section names are dependencies, detection, events, metadata, outputs, parameters, schema, semantics, state_machine, tokens, view_extensions; each trait uses the sections it needs. The table below explains the core sections using Stateful as the example:

SectionWhat it declaresStateful's actual content
parametersSettings the object sets when it uses the trait (typed, with defaults and validation).states (ordered list), initialState (must be one of states), transitionRules (allowed from→to map; open when omitted), requireTransitionReason
schemaThe data fields the trait adds to any object that uses it.status (one of states), state_history (from, to, timestamp, actor, reason), allowed_transitions (computed next states)
semanticsWhat each field means (a semantic type), which token group styles it, and the default component for it. The screen composer uses this to pick a component for any field no view extension covers.status → status.state → StatusBadge · state_history → timeline.state_transition → StatusTimeline · allowed_transitions → StatusSelector
view_extensionsWhich UI piece to show in each context, where, and with what props.list: StatusBadge · detail: StatusTimeline (top, priority 40) · form: StatusSelector · timeline: StateTransitionEvent · card: StatusBadge
tokensThe styling hooks those pieces use, pointing at system tokens. Merged into the object and carried into every rendered screen as token overrides.status.timeline.connector → var(--border-subtle), status.timeline.node.bg → var(--sys-surface-raised) …
dependenciesTraits that must be present first.none — but Archivable, Auditable, Cancellable and Colorized all depend on Stateful
metadataMaturity, owners, accessibility notes (keyboard, screen reader), who composes it.stable · "StatusSelector is keyboard-navigable (arrow keys, Enter)"

How a trait works once applied

An object names the trait and sets its parameters — Product's file says:

- name: lifecycle/Stateful
  parameters:
    states:
      - draft
      - in_review
      - active
      - retired
    initialState: draft

From that, Product gains a status field restricted to those four values, a transition history, and a computed list of next states; every Product list shows a status badge, every detail page a status timeline, every form a status selector whose options come from the object's own states. Parameters flow into component props (optionsParameter: states), so the same StatusSelector is correct for Product's four states and Subscription's eight. Parameter values are checked against each trait's JSON Schema (schemas/traits/<name>.parameters.schema.json) when the full engine resolves an object — pnpm object:validate, object:compose, object:generate; the tools' lighter composer merges without validating, so run object:validate after editing an object.

04Objects and composition

Object

A YAML file naming a thing you model, listing the traits it has (each with its parameter values), and declaring the handful of fields that are genuinely its own. Objects do not hold records — they hold the definition Forge builds screens, charts and types from.

The Product object (objects/core/Product.object.yaml), in its real shape with most traits elided:

object:
  name: Product
  domain: core.catalog
traits:
  - name: content/Labelled
    alias: ProductLabel
  - name: lifecycle/Stateful
    parameters:
      states:
        - draft
        - in_review
        - active
        - retired
      initialState: draft
  - name: financial/Priceable
    parameters:
      supportedCurrencies:
        - USD
        - EUR
        - GBP
        - AUD
      defaultCurrency: USD
      pricingModels:
        - one_time
        - subscription
        - usage_based
      billingIntervals:
        - one_time
        - month
        - year
      taxBehavior: exclusive
schema:
  product_id:
    type: uuid
  sku:
    type: string
  inventory_status:
    type: string
  release_channel:
    type: string
  requires_subscription:
    type: boolean
  support_level:
    type: string
  summary_blurb:
    type: string
# Other traits: lifecycle/Timestampable, core/Classifiable, behavioral/Searchable, behavioral/Filterable, behavioral/Pageable

An object may also carry its own semantics and tokens sections, which override the traits'.

What composition does

When Product is composed:

  1. Fields are merged — every trait's schema fields plus the object's own: 38 fields for Product. If two traits declare the same field, the full engine applies collision rules (same type → merge, keep the stricter; two enums → union; required beats optional; different types → error unless the object resolves it) and records which trait each field came from.
  2. Parameters are applied — validated against each trait's schema, and parameter-driven enums become real constraints (Product's generated TypeScript type has status: 'draft' | 'in_review' | 'active' | 'retired').
  3. UI contributions are collected per context — all traits' view extensions grouped by context and sorted by priority, giving a ready list of what to show on each kind of screen.
  4. Tokens, semantics, actions and a state machine (multiple owners are refused by default) are merged.

The full engine (src/core, src/registry; the object:* commands) performs the composition steps above. The tools' runtime composer (packages/mcp-server; what object show and design.compose use) merges schema, semantics, view extensions and tokens only — last-wins on collisions with a warning, no parameter validation — and orders extensions higher-priority-first (default 0), where the React view engine orders lower-first (default 50).

06Contexts, regions and components

Context

The kind of screen an object is being shown in. A trait's view extension names the context it targets, so the same object produces a different — but consistent — screen for each. Traits contribute to list, detail, form, timeline, card and inline. Bound bar and line traits also author dashboard contributions, selected through the public dashboard layout. The chart view remains a shell.

Every context in Forge's component library is laid out on the same six named regions, in this order: globalNavigation, pageHeader, breadcrumbs, viewToolbar, main, contextPanel. Main is always required; page header is required in every context except card and inline; list and timeline also require the toolbar. Regions render as real HTML landmarks (nav, header, main, aside with labels), so structure is visible to screen readers and testable.

How a screen is assembled. For the requested context, Forge collects every trait's extensions, sorts them by priority (lower first, default 50; ties by declaration order), evaluates any conditions (data, permissions, theme), groups them by region and composes them in a fixed order. Each rendered piece is wrapped in a boundary carrying its id, region and source trait, and a debug mode prints a per-region report. Below tablet width (768px container) the two-column contexts collapse to one column; an opt-in drawer component turns the side panel into a focus-trapped sheet.

There are two renderers. The React view engine (the component library, Storybook, the region contract above) and the tools' HTML renderer, which places the same trait contributions into layout templates — dashboard, form, detail, list, card, timeline, landing — with named slots (header, tab-N, metadata, items, filters, hero, cta …). Generated HTML documents carry the tokens and components, not yet the six-region responsive shell.

07Tokens, themes and brands

Token

One named design value — a colour, size, font, duration, breakpoint — authored once in the W3C Design Tokens format (DTCG JSON, under packages/tokens/src/tokens/) and compiled to every platform. Components never contain raw values; they reference tokens.

One build (pnpm build:tokens, Style Dictionary) compiles the JSON sources into five outputs: CSS custom properties (1042 variables), a TypeScript map, a Tailwind token map, a Swift file and a Kotlin file. Tokens are layered so that a change at the right level propagates:

--ref-color-neutral-50: oklch(0.985 0.002339 265);
--theme-surface-canvas: var(--ref-color-neutral-50);
--sys-surface-canvas: var(--theme-surface-canvas);
--cmp-text-placeholder-color: var(--sys-text-muted);
--sys-breakpoint-md: 768;

Themes are light, dark and high-contrast (the last maps to the operating system's forced colours). Brands are sets of values for the brand colour roles — surfaces, text, interactive, borders, status and focus — one JSON file per brand per theme (the base files contain 45 leaves each, under brands/<X>/{base,dark,hc}.json). The build emits a block per brand × theme that re-assigns 41 shared theme slots to that brand's values:

[data-brand='B'][data-theme='dark'] { --theme-surface-canvas: …; --theme-text-primary: …; … }

So switching brand or theme is two attributes on the document; no component changes. Two brands ship today (A and B); three brand-relative presets (corporate-blue, dark-minimal, startup-warm) can be applied to any brand. brand.intake validates inline brand-relative DTCG documents and returns an envelope hash plus a consumable delta for accepted A/B themes. brand.apply previews that delta or writes canonical brand source and runs both token-build stages, retaining source hashes, byte counts and captured build results in a dated review folder. A failed build reports the output tail and leaves source writes in place. tokens.build returns requested-scope JSON and CSS alongside full CSS and legacy A/light TypeScript and Tailwind artifacts.

Guards around the build. A collision guard refuses to build if two source files declare the same token with different values; 228 brand-contrast rules (57 text/icon pairs per brand per theme) run in CI, and any theme slot a brand newly overrides must be graded; a real-browser check asserts the computed values in all six brand × theme cells; a CI check blocks high-risk token changes (by namespace and segment) unless the PR carries the token-change:breaking label.

10Certification and checks

Certify

artifact.certify takes a chart specification back (and, for the advanced types, its data) and returns a per-check scorecard plus a combined conformance result on the declared certification path. Its four core certification pillars are accessibility equivalence, determinism, contrast and accuracy.

Core certification pillarWhat is actually tested
Accessibility equivalence16 structural rules over the chart and its text alternative: colour encodings carry a second cue and size differences are perceptible; an accessible table exists, captioned to the chart title, with declared column order; axis titles, an accessible name and a description at least 25 characters are present; bar/stacked charts narrate extrema, trend charts narrate the trend, area charts describe their baseline/range; datasets with 3+ rows surface at least two findings and dense ones aggregate; every encoded field is present in every row; the narrative generator reports ready; interactions describe their announcements. Each rule names its precondition; absent preconditions remain visible as not applicable. On the data-backed ECharts path, error-severity failures fail the accessibility pillar and conformance; warning-severity findings remain visible without failing the pillar.
DeterminismTwo independent compiled or projected specifications are canonicalised and byte-compared, then independently rendered SVGs are compared. Content and render hashes identify the corresponding viz.render output for the same operand and scope; notes retain any rendering limitation and the certified runtime boundary.
ContrastThe colour values actually baked into the spec are graded: every mark at least 3:1 against the requested light or dark theme canvas (WCAG 1.4.11); categorical palettes checked for distinguishability under normal vision and three colour-vision-deficiency simulations; gradient scales reported as exempt, not passed. The requested A/B brand and light/dark/hc theme are retained. High-contrast returns an exempt contrast result with reason forced-colors and no numeric grade; the browser resolves the declared system colours.
Accuracy16 reader-only structural-distortion rules: bar baseline not at zero (or on log/sqrt); dual y-axes in one frame; area on a non-linear scale; a row-merging aggregation not disclosed in title, description or axis; negative treemap/sunburst values; a parent not equal to the sum of its children; negative sankey/chord links; sankey node height inconsistent with its flows; duplicate sankey links; conflicting values joined to one map region; invalid bubble sizes and flow strengths, radius-based bubble scaling, duplicate geographic operands, and overlapping duplicate directed force-graph links. Reciprocal links remain distinct. "Pass" means no offered rule detected its distortion, and the count of rules that actually ran is reported. ECharts accuracy requires at least one evaluated rule; missing preconditions never count as a pass.

Coverage, stated plainly. The five Cartesian types certify from their IR. Advanced types use the declared operand profile with the same data supplied to rendering: conformance requires accessibility to pass, contrast to be neither failed nor ungradeable, stable determinism, and evaluated-and-clean accuracy. Certified coverage can carry a measured false conformance result. Spec-only ECharts calls remain uncertified with null conformance and a missing-operand explanation; this path adds no Vega-Lite compile. Certification covers chart specs, not pages or components. It accepts brand A or B and theme light, dark or hc (defaults A/light), matching rendering and contrast grading. High-contrast SVG proof covers bar, line, area and scatter. Heatmap and the eight ECharts types retain typed undeclared-paint failures; their render failure fails determinism and conformance. HC contrast alone is exempt with reason forced-colors. Forced-colours browser evidence covers chart SVGs, dashboard HTML and the React/Vue Subscription detail preview.

Other checks

  • Token contrast — a11y.scan (and repl validate on request) grades 18 token pairs: primary text on canvas / raised / subtle surfaces, secondary, muted, accent and inverse text, the four status text and four status icon pairs, and three dark-theme primary-text variants — 4.5:1 for text, 3:1 for icons.
  • Component library in CI — axe-core (WCAG 2.0 A + 2.1 AA, serious/critical) over a fixed set of Storybook stories in light and dark; Playwright behavioural checks at phone (375), tablet (768) and desktop widths (layout collapse, drawer focus trap, Escape to close, no violations with the drawer open); the brand-contrast and browser checks from section 07; optional Chromatic visual regression.
  • Native tokens — the Swift and Kotlin outputs are compiled with the real toolchains before a release (a shape test runs in CI).

12Extending it — and what it does not do

  • New trait: traits/<family>/<Name>.trait.yaml (the suffix is required) plus schemas/traits/<name>.parameters.schema.json, and the components its view extensions name; pnpm validate --path traits checks the library. Runbook: docs/authoring-traits.md.
  • New object: objects/<group>/<Name>.object.yaml (or a domain pack) naming traits and parameters; pnpm object:create scaffolds it; the server indexes it on its next start. Runbook: docs/authoring-objects.md.
  • New domain: a folder under domains/ with its own traits and objects (the SaaS-billing pack is the model).
  • New brand: packages/tokens/src/tokens/brands/<X>/{base,dark,hc}.json plus aliases/brand-<X>.json and entries in the build config (style-dictionary.config.cjs: brand scopes and shared base list); the tool schemas' brand enum and the CI matrix are widened; pnpm build:tokens then emits the brand's blocks, and the contrast rules and browser check cover it.
  • New components: React source + story, a renderer entry in packages/mcp-server/src/render/component-map.ts, and a trait view extension naming it (primitives are listed in the refresh script); pnpm refresh:data republishes the catalog the tools read.
  • An outside component library: describe it with map (component → trait, prop translations) so its vocabulary resolves to trait terms via map resolve and registry.snapshot.

What Forge does not do

  • No data storage or backend — objects are definitions, not records; there is no runtime data binding.
  • No language model inside — intent matching is rules and synonyms; the AI assistant sits outside and calls tools.
  • No hosted service — the server runs from a checkout or the extracted portable bundle and the bridge binds to localhost.
  • Certification covers chart specs only, scoped to the requested A/B brand and light/dark/hc theme (HC contrast is forced-colors exempt); ECharts calls without the matching data operand remain uncertified with null conformance; pages and components get contrast rules and CI audits, not certificates.
  • Generated HTML documents use the tokens and components but not the six-region responsive shell; code generation targets React, Vue and HTML only.
  • Typography shares global sans and display font stacks. The categorical chart palette resolves by brand and theme and accepts explicit token overrides. The Swift/Kotlin files carry one default brand × theme and omit font stacks and easing curves.
