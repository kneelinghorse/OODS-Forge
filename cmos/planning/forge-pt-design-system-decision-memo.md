## Recommendation

**A third shape: develop Parts Town as a brand inside Forge, but deliver it as a client-owned artifact repository — DTCG tokens, built theme CSS, and hosted docs — that Parts Town's team consumes without ever touching Forge.** Do not fork the monorepo. Do not stop at "just add a brand" either, because the thing a brand-in-core produces today never leaves the repo in usable form.

The short version: **Forge is the factory; Parts Town gets the products, and owns the shelf they sit on.**

### The five factors that drive this

1. **Enterprises consume artifacts, not foreign monorepos.** Every delivery pattern the research found has enterprise teams consuming versioned packages, tokens, docs, and Figma libraries (UXPin/Sparkbox/Knapsack practice); none has a client team adopting an outside consultant's build environment (an absence-of-evidence claim — nothing found, not proven impossible). Forge's own audit confirms the runtime cannot travel anyway: the MCP server reads live repo directories from a full monorepo checkout (17 `REPO_ROOT` resolution sites, e.g. `packages/mcp-server/src/objects/object-loader.ts:13`), and the bridge binds to `127.0.0.1` only (`packages/mcp-bridge/src/server.ts:359`). There is no Dockerfile anywhere.
2. **Parts Town's stack makes framework-neutral tokens the right deliverable.** Their live site is a SAP Hybris/JSP accelerator storefront on jQuery 2.2.1 with Vue traces (verified by fetch of partstown.com, 2026-08-01). SAP's modernization path is Angular-based composable storefront (https://github.com/SAP/spartacus). A React component library is the wrong primary deliverable; DTCG tokens → CSS variables survive a jQuery → Vue → Angular re-platform. That is exactly Forge's most standards-aligned layer (DTCG 2025.10 is now stable: https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/).
3. **Deliverable shape ≠ development shape — this is the industry-normal pattern.** Westpac GEL serves four bank brands from one monorepo but ships consumers a small number of npm packages (two, per the research pass) (https://github.com/WestpacGEL/GEL-next); GOV.UK ships `govuk-frontend` to every department (https://github.com/alphagov/govuk-frontend); NL Design System proves white-label core + per-org theme across fully independent organizations (https://nldesignsystem.nl/handboek/developer/architectuur/). Derek keeps his engine; the client gets outputs.
4. **A fork inherits Derek's operational life.** The repo carries 8.5 GB of `cmos/` with 730 git-tracked files including ~750 MB of operational SQLite databases in tree and history, personal portfolio research (`designs/derekn.com-portfolio-refresh-v1.yaml`), an aquex.ai-branded dark theme (`packages/tokens/src/tokens/brands/A/dark.json:10`), and the Meridian Gate 5 deliverable with its independence-protocol receipt (`artifacts/domain-models/parts-commerce/RECEIPT.md:3-4`). Sanitizing that for handoff is a git-history rewrite, and afterward Derek pays the divergence bill alone (https://www.architecture-weekly.com/p/you-can-fork-a-package-but-can-you).
5. **Tokens are the cheap-exit kernel.** The standard consolidation compromise is "converge on tokens, keep separate systems above" (Nathan Curtis, https://medium.com/eightshapes-llc/consolidating-design-systems-6bb7ce72f393). Starting PT as DTCG-in-a-client-owned-repo means the "developed elsewhere later" scenario is an extraction, not a divorce.

## The options, honestly

### Option 1 — Full fork of Forge into a PT repo. **Rejected.**

- **Pros:** Total insulation of Forge from client-shaped requirements ("most-demanding-brand capture," Grönboldt: https://uxdesign.cc/challenges-of-multi-brand-design-systems-42d7e7b1d18c). Client independence from day one.
- **Cons:** The client's team cannot run it — the constraint is stated, and the audit confirms the run-it-locally surface (pnpm monorepo + pm2 bridge with no ecosystem file in the repo + loopback-only server) is single-operator machine state. The fork carries everything in factor 4 above plus machine-path provenance strings (`generated/objects/User.d.ts:6`). Two publishable packages ship without LICENSE files (viz-core, viz-render). And a fork of a system whose brand mechanism is only half-built (see Option 2) forks the gaps too. The agency-handoff guidance found (practitioner blogs, consistent but not authoritative) recommends the transfer artifact be a repo the client's org owns with a credentials inventory — a 15 GB working tree with the consultant's mission history is not that.

### Option 2 — PT as a brand inside Forge, and nothing else. **Necessary but not sufficient.**

- **Pros:** The architecture is genuinely the right kind — DTCG + Style Dictionary + `data-brand`/`data-theme` is the same stack Westpac runs at bank scale. Two brands (A, B) already exist (`packages/tokens/src/tokens/brands/{A,B}/`), so PT is an incremental brand; one practitioner estimate puts brand #3 at 10–20% of the initial build (Grönboldt — single source, treat as anecdote, not a cost curve).
- **Cons — the capability audit shows the brand mechanism doesn't reach a client today:**
  - The packaged CSS is brand-blind: `dist/css/tokens.css` is a single `:root` block with zero `[data-brand]` selectors; the switching CSS is hand-authored app-layer code (`apps/explorer/src/styles/brand.css:2`) with **already-drifted values** vs. the token source (brand.css:11 `oklch(0.56 0.19 45)` vs `brands/A/base.json:41` `oklch(0.58 0.19 43)`), and no generator script exists.
  - The MCP tool surface hard-locks brand to "A" (`packages/mcp-server/src/schemas/brand.apply.input.json:5-9`), `brand.apply` cannot create a brand and does not write back to token sources despite what `docs/theming.md:44-67` claims, and MCP-rendered documents ship only the `:root` CSS — the `data-brand` attribute is inert in rendered output (`packages/mcp-server/src/render/document.ts:20`).
  - Per-brand gaps with no hook at all: fonts (zero `@font-face` anywhere; Inter hardcoded in `tailwind.config.ts:24-33` — PT's Museo Slab/Effra cannot be loaded), viz palette (one fixed palette, `packages/tokens/src/viz-scales.json`), radii/spacing/elevation, and brand assets (logo/favicon).
  - Bottom line: a PT brand built this way lives and dies inside Derek's checkout. It serves no team.

### Option 3 — Brand-in-Forge development + client-owned artifact repo delivery. **Recommended.**

- **Pros:** Matches every working precedent (GEL-next, GOV.UK, NL Design System). Deliverables are framework-neutral and survive PT's likely Angular re-platform. Procurement-clean: a small scoped package (`@partstown/tokens`) with a tiny dependency tree passes an enterprise Artifactory allowlist review far faster than anything else on this list (https://vulert.com/blog/internal-package-registry-security/, https://www.wiz.io/blog/practical-package-security-the-unofficial-guide). The client owns the GitHub org and npm scope from day one, so "developed elsewhere later" is already true structurally. Cost of goods is small (GitHub Packages free tier; Chromatic reported free–$179/mo for the team-facing Storybook — all pricing figures in this memo are agent-reported and unverified; recheck at decision time). The parts-commerce domain model (`artifacts/domain-models/parts-commerce/` — 5 objects, 4 traits, SHA receipt) already proves the file-plus-receipt delivery pattern works for this client relationship.
- **Cons:** Derek takes on publisher obligations — semver, changelogs, migration guides, support windows (https://guides.inedo.com/npm-enterprise/versioning/). Real packaging work is owed first: the `@oods` npm scope is unclaimed (npm 404s verified), there is no publish CI (workflow list checked), brand-switching CSS must move from the app layer into the tokens package build, and the font/viz-palette gaps from Option 2 must be closed because PT's brand needs them. This is the honest cost of the recommendation: roughly the Section 2 gap list — new brand dirs, a real brand-CSS generator, enum widening in 3 schema/type files, a font pipeline.
- **A worthwhile variant to keep in pocket:** shadcn-style source delivery — Forge generates, the client repo owns the emitted source, updates are re-pulls not semver upgrades (https://ui.shadcn.com/docs/registry). This fits Forge's generate-and-certify identity and eliminates the ongoing supply-chain surface enterprises scrutinize. Decide between "npm package" and "generated source drop" after learning PT's registry policy (open question below); the token layer is identical either way.

### Option 4 — Hosted Forge service (remote MCP endpoint for PT). **Phase-2 at most, not the decision.**

- **Pros:** Real product precedent arrived in 2025 — Supernova Relay and zeroheight both ship hosted design-system MCP endpoints (https://learn.supernova.io/latest/releases/september-2025/introducing-supernova-relay-lWfNcpwJ, https://zeroheight.com/mcp/). Nobody found is selling *generate-and-certify* over MCP — that would be Forge whitespace. Infra cost is trivial (Cloudflare Workers ~$5/mo + WorkOS AuthKit free tier).
- **Cons:** Architecturally furthest from today: loopback-only bridge, child-process spawn from a sibling workspace path, repo-local artifact serving, optional auth (`packages/mcp-bridge/src/config.ts` nullable token), no containers. Derek becomes a vendor-of-record with uptime and security-review obligations, and PT's enterprise IT must approve an external AI endpoint holding their design data. Do not let this shape gate the engagement; revisit after the artifact pipeline is live.

## Derek's constraints, one by one

- **Enterprise environment; client team cannot run Forge locally.** Solved by construction: PT's team receives a package/theme-CSS + hosted Storybook + docs. They never install pnpm workspaces or pm2. The audit's "fundamentally local" list (mcp-server, bridge, certify, brand.apply) stays on Derek's machine, where it already works.
- **Must serve a team.** The team-facing layer is the delivery repo plus hosted, access-controlled docs: Chromatic (permission-synced private Storybook, free tier to start) or zeroheight ($49/editor/mo, free viewers, Sparkbox-validated consultancy channel). Governance docs ship with it from day one — contribution/RFC model, review, versioning policy. Operating model: Derek is the core team; PT devs/designers file requests; Derek reviews and releases (Zalando-style centralized-early model).
- **Might be developed/hosted elsewhere later.** This is the strongest argument for the recommendation. DTCG 2025.10 tokens in a PT-owned repo are portable to any future stack or vendor by design. The insourcing exit is: PT's repo becomes the source of truth and their tooling connects to it (the Knapsack pattern) — an extraction Forge's shape keeps cheap, versus a fork where the exit is untangling Derek's history from theirs.
- **Derek starts it and may host it.** Hosting under this shape means: a GitHub org + package registry + Chromatic/static docs — all commodity, all transferable per the agency-handoff literature (client must end up owning org, scope, and credentials). If Derek later hosts a live Forge endpoint (Option 4), it layers on without changing the deliverables.
- **Figma files in hand.** There is no Figma import in Forge today — Figma tooling is export-only (`scripts/viz/export-figma-handshake.ts`; `docs/viz/figma-handshake.md:23-24`). The ingestion pipeline is external and plan-tier-dependent; it is Move 1 below. Critically, styles-based files are fully extractable on any Figma plan via plain REST (`GET /v1/files/:key/styles`, https://developers.figma.com/docs/rest-api/file-endpoints/) — only the Variables REST API is Enterprise-gated.

## First three moves

**Move 1 — Figma → DTCG ingestion (week 1–2).**
First, determine PT's Figma plan tier; it sets the whole pipeline (Variables REST API and Extended Collections are Enterprise-only; Code Connect is Org+; plugins work everywhere). Baseline path that works on any plan: (a) extract the styles inventory via REST or an export plugin; (b) convert styles → variables in-file with community plugins ("Styles to Variables Converter" + a rebinding pass — noting only solid/alpha colors convert; gradients/multi-fill stay styles or become code-side tokens); (c) tokenize to DTCG with Tokens Studio (Pro-tier plugin) syncing to a git repo via PRs — **use git-sync into the client-owned repo, not Tokens Studio's cloud sync: routing PT design data through third-party SaaS needs the same enterprise-IT clearance as any hosted option, so default to the procurement-clean path**; (d) build with Style Dictionary — Forge pins `^4.4.0` (package.json:207), which already reads DTCG; a v5 upgrade is optional, not a prerequisite. Effort anchor: one practitioner blog reports 1–2 weeks for a 200–500-token inventory (low confidence — re-estimate after actually opening PT's Figma files); full component rebinding is the long tail. Check in-app whether Figma's native DTCG export has landed on their account (announced Schema 2025, shipping timeline conflicting: https://figma.obra.studio/design-tokens-community-group-w3c-release/); treat it as a bonus, not a dependency.

**Move 2 — Make Forge's brand pipeline real for a third brand (the engine investment). Rough size: 2–4 focused weeks solo (±50%, unvalidated) — this is the largest engineering item in either front and competes with the mobile crawl for the same operator.**
The honest beneficiary is PT alone today (brand A is Derek's own aquex skin; brand B has no named consumer) — but this same work closes the fidelity pillar's documented "brand seam is a no-op" gap from the s144/s145 review, so it remains real engine value even if the engagement dies. Close the gaps the capability audit found, in Forge: generate `[data-brand]` CSS from token sources into the tokens package build (killing the hand-authored, already-drifted `brand.css`); widen the brand enum out of `["A"]` in the three schema/type files; add `brands/PT/{base,dark,hc}.json` + alias layer; add a font-loading hook (PT needs Museo Slab/Effra; nothing can load a brand font today); decide the viz-palette binding (per-spec override exists via `spec.config.tokens`, but PT chart colors deserve a brand-level home). Ship the result as the first cut of the PT theme CSS.

**Move 3 — Stand up the PT delivery repo and pilot one real surface.**
Create the client-owned org/scope (or Derek-held-in-escrow with a written transfer plan), publish `@partstown/tokens` (DTCG JSON + built CSS variables + Tailwind mapping), stand up the private Storybook (Chromatic free tier — note Chromatic and zeroheight route PT design artifacts through external SaaS; clear that with PT IT alongside the registry question, with static Storybook on client-owned infra as the fallback), and include governance docs. Then follow the consultancy doctrine: prove it with a pilot on one real product surface before scaling (Dan Mall: https://danmall.com/posts/). The natural pilot is a parts-commerce screen — the domain model already defines the views (ReplacementBanner, FitVerifier, SpecificationTable, `MODEL.md:73-85`) — composed in Forge, skinned with the PT brand, delivered as certified static output with a SHA receipt, the same pattern that already worked for Gate 5. Note the model is currently a frozen artifact, not registered in the live registry; registering its objects/traits is a prerequisite for composing those screens through Forge tooling. **Pilot fallback:** if the Meridian Gate 5 boundary (open question 7) blocks reusing the parts-commerce model before their reconciliation completes, pilot instead on a generic commerce surface composed from Forge's existing object registry (no Gate-5 lineage), and swap the domain model in once the boundary clears — the delivery mechanics being proven are identical.

## Risks to carry into the decision

- **Divergence cost.** Unreconciled brand overrides quietly become permanent forks (Southleft; architecture-weekly). Mitigation: the PT brand's source of truth is DTCG in the delivery repo, rebuilt through Forge — one direction of flow, no hand-copied CSS. The drifted `brand.css` value is the proof this risk is already live inside Forge.
- **Maintenance burden.** The dependency path makes Derek a publisher: semver, changelogs, migration guides, support windows — real recurring cost for a solo operator. Mitigation: system-level versioning (one version for the whole system), a maintenance retainer priced as availability not hours, and the source-drop variant if PT prefers owning code to consuming releases.
- **IP / licensing.** Root license is MIT under generic "Design System Team" — clean. But viz-core and viz-render declare MIT with no LICENSE file (fix before anything ships), and the engagement contract must state what PT owns (their brand tokens, the delivery repo, generated source) versus what Derek retains (Forge, the engine). A fork would have made this murky; the artifact shape keeps the line crisp.
- **Certify-pillar coupling.** `artifact.certify` is only reachable inside the local MCP server, and MCP-rendered documents currently ignore `data-brand` entirely — so today, a "certified" render is certified in default skin, not PT's. Until the brand-aware render gap closes (Move 2), certification claims about PT-branded output would be overclaims. The honest interim: certify what is actually baked into the artifact, ship it with the SHA-receipt pattern, and treat brand-aware certification as the milestone where Forge's differentiator (generate-and-certify — no shipping MCP design-system product offering it was found; absence claim) becomes real for this client. **The client-side driver to probe:** PT is US e-commerce, where WCAG/ADA accessibility compliance is a heavily-litigated area — if PT has compliance exposure or appetite, certified-accessible output is something they buy for their own reasons, not a Forge vanity feature. Whether that exposure/appetite exists is a client question (added below).

7. **Meridian Gate 5 boundary:** does the reconciliation protocol around the parts-commerce model constrain reusing it in a paid PT engagement before Meridian's reconciliation completes? (Fallback pilot exists either way — Move 3.)
8. **Does PT need mobile — native app or a mobile-web push?** This is the single concrete coupling to the mobile front: its walk/run phases hang on a real native consumer existing, and PT is the only candidate visible today. Ask it in the same conversation as Q1–Q6.
9. **Does PT have WCAG/ADA compliance exposure or appetite?** Decides whether certified-accessible output is a purchasable deliverable or an internal quality bar.
