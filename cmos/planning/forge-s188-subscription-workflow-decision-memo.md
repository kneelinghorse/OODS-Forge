## 1. What this sprint is

Two things, in this order, because Derek chose them on 2026-09-07:

**(a) Ship.** Put the merged Sprint 187 build on the live bridge. Today PM2 serves the primary checkout at
`8ce34907`, which predates Sprints 183–187: nobody using Forge through the bridge can reach the 64 governed
components, the 66/66 fresh composition or the current catalog. Adopt the authentic User-form successor
record, resolve the served `schema/load` failure, and send the one combined reconnect the last three sprints
prepared and never sent. This closes carries #1374, #1379 and #1384.

**(b) Make the Subscription app whole.** Generate, from the public object/context inputs alone, a runnable
Subscription application in React and in Vue: list → detail → edit → cancel → timeline, with loading, empty,
error and success states on every screen and navigation between screens generated by Forge, not written by
the consumer. Give the Subscription screens the billing and archive components their traits declare and no
implementation has ever provided. This is Increment 3 finished in the words of its own gate, and the first
artifact that answers "does Forge have usable parts?" with something a person can click through.

## 3. Anti-circularity

Every screen of the application is the unmodified output of the public composer for `{object:'Subscription', context}`
over the six public contexts; the workflow assembly, routes, state branches, store and sample data are emitted by
Forge product code from the composed object and its traits. No schema is hand-authored, no saved-store record is
edited, and the harness contributes nothing but the packed artifact, a browser and observations. The Sprint 184
objection — that an edit/cancel/timeline schema would have to be authored — no longer holds because fresh
composition is certified for those contexts.

## 4. Settled decisions (planning decides; the builder does not re-plan)

1. **Served checkout = the primary checkout, fast-forwarded.** The primary is clean and a strict ancestor of
   `OODS-pro`; `git merge --ff-only origin/OODS-pro` on `Forge-expansion`, rebuild in place, `pm2 restart
   oods-forge-bridge`, `pm2 save`. No second deployment tree, no ecosystem-file migration. The Sprint 187
   rollout packet's backup, precondition, verification and rollback steps apply verbatim; its worktree step
   is replaced by this one. The schema store and `.env` are untracked and untouched by the fast-forward.
2. **Delivery proves the compiled revision by discriminating behavior**, not by green health: `catalog_list`
   returns `obligationScope` with 109 rows; `code_generate` of a Sprint 187 family (ArchivePill) is governed in
   both targets; public `schema/load` of a saved record returns 200 with a matching hash; checkout HEAD equals
   `cd8ee986` and built-file hashes are recorded. A `/health` revision field (build commit + structured-data
   manifest hash) is added by this sprint's code for the next delivery, never used to attest this one.
3. **Adoption** replaces only `user-form-showcase.json` and its index entry with the reviewed successor from
   `artifacts/product-reality/sprint-187/m05/delivery-final/recomposed-store/`, with the byte preconditions in
   `recomposition.json`, after a full hashed backup of the store; the other 15 records and index entries are
   byte-identical after adoption; rollback restores the backup.
4. **One combined reconnect** to `cmos://derek/aquex-mcp` and `cmos://derek/forge-demos` after delivery,
   carrying the served identity, the Sprint 184–187 advertised movers and the `obligationScope` addition.
   Dashboard Demos stays retired (#1719).
5. **Workflow composition is a seventh public context.** `design.compose({object, context:'workflow'})` returns a
   multi-screen `UiSchema`: the existing list/detail/form/timeline compositions as screens with `route`
   (`/`, `/:id`, `/:id/edit`, `/:id/timeline`), a top-level `workflow` block (object, screens, transitions,
   states, data), and the four canonical state branches added to every screen using the Sprint 184 contract.
   The six existing contexts remain byte-identical (pinned by the census). Card and inline are not screens.
6. **Transitions come from the screens' own actions.** `handleRowClick(id)` → detail; `handleEdit` → form;
   `handleSubmit` → save → detail; a trait-declared `handleCancel` on detail and form (Cancellable) →
   store transition to `pending_cancellation` with reason/code/at-period-end → detail; `handleViewTimeline`
   on detail (Timestampable/Stateful) → timeline; `handleDelete` is bound to archive (Archivable) and reversible.
   Actions the composer already declares keep their names; the two new ones are declared by the traits, not by
   the assembler.
7. **Application emission** in both emitters when `workflow` is present: an `App` root with generated local
   navigation state (current screen + selected id; `route` recorded, no URL routing and no router dependency
   this sprint), a typed in-memory domain store per object generated from the composed schema and traits,
   deterministic sample data (10 subscriptions covering all eight lifecycle states, both intervals, all
   payment statuses, one archived), simulated latency for loading, an empty-seed mode and an injectable
   failure mode for the error state, an entry file and a runnable package manifest. Every emitted import
   resolves to a Forge artifact or the declared framework peer. Router adapters are a named follow-on.
8. **The eight rows are implemented from the trait declarations as authority** (there is no HTML to port):
   contract + shared scenarios + prop-value contracts + HTML renderer in `component-map.ts` + React + Vue +
   token styles + readiness rows + value-level tests, the Sprint 185 bar. Amounts are minor units formatted
   with `Intl.NumberFormat` and the trait's `minorUnits` parameter; `BillingAmountInput` edits major units and
   stores integer minor units, rounding half-up, rejecting negatives, allowing zero. `BillingIntervalSelector`
   options come from the `billingIntervals` parameter with keyboard navigation and a typed update.
   `CycleProgressCard` uses `current_period_progress` when present, otherwise computes from period dates with
   an injected `now`, and announces percentage plus remaining days. `PaymentTimeline` and `PaymentEventTimeline`
   are two public IDs over one shared timeline primitive, both retained; no alias, no exclusion, denominator
   unchanged. `ArchivedRowOverlay` greys archived rows, badges them and separates them into an "Archived" tab.
   `TimelineEntryLabel`, `SortIndicator` and `AuditSummaryCard` are outside the Subscription flow and stay carried
   by name with their objects' flows as the trigger.
9. **Labels are real.** The composer's label generator uses the object's field descriptions, then humanized
   field names; "Field N" is never emitted for a bound field. Regression-pinned across all 66 schemas.
10. **Catalog truth for the nucleus.** The structured-data projection reads the foundation-v1 and closeout
    records for the 14 nucleus rows so `catalog_list` reports both frameworks as implemented with evidence;
    frozen s182 records are not rewritten. Refresh runs at the sprint head.
11. **Evidence bar and pace.** Per family: typecheck, package tests, packed proof, cross-framework parity, one
    export bite. Per screen: the eight consumer gates from the live harness. For the application: one packed
    consumer per framework mounting the generated `App`, driven through the entire flow by the harness with
    state markers observed on every screen, plus screenshots at 390, 820 and 1440 px widths for the independent
    craft review. One four-suite capture at close. No per-mission captures, no new closeout framework, no
    critic workflow.
12. **Delivery cadence from here:** each sprint's first mission delivers the previous sprint's reviewed and
    merged head. This sprint's own code reaches the bridge in Sprint 189 m01.

## 6. Exit gate

From the program authority, verbatim: *"The same semantic workflow is usable in both frameworks with loading,
empty, error, and success states."* And criterion 8: *"At least one complete greenfield application is generated
and usable in React and Vue."*

Sprint 188 meets the first sentence in full for Subscription (list, detail, edit/cancel, timeline) and opens
criterion 8 with one application. **"Usable" is decided by the independent review's responsive/craft
inspection of the rendered screenshots and the live consumers, not by the build.** The sprint does not claim
persistence, a backend, URL routing, permission-aware or confirmation primitives, responsive maturity of the
64 families, or accessibility/theme/interaction maturity beyond what the harness gates observe.

## 7. Descope ladder (declared now, in order)

1. Drop `BillingCardMeta` and `PaymentEventTimeline` (card and timeline contexts); the timeline screen shows
   `state_history` and cancellation events only.
2. Drop `ArchivedRowOverlay`; `handleDelete` stays bound to archive without the list overlay.
3. Drop the empty-seed and failure modes from the generated shell and prove empty/error from data conditions the
   store already reaches (zero results after filter; invalid transition).
4. Prove the craft screenshots at one width (1440) and name the other two unproven.

**Never cut:** m01 in full; both frameworks; the four states on list, detail and form; the cancel transition
visible on three screens; generated navigation with no consumer-authored component or wiring.
