## Decision 1 — License and first-party notice scope

Choosing different terms requires a separately specified first-party scope and review of the rights needed for that distribution. **One-way-door status.** No new license decision has been made here. Source metadata can be edited later, but publicly distributed copies and the terms accompanying them cannot be treated as recalled merely by changing the repository.

**Proposed decision text, pending Derek:** “Retain the existing license fields and LICENSE files for this private release proof. Gate 2 license approval remains pending. **Proposed decision text, pending Derek:** “Keep public npm publication and MCP Registry submission deferred. ## Decision 6 — Disambiguate “manifest on health”

**Measured facts.** There are two different requested surfaces and a third existing provenance field:

| Surface | Implemented meaning |
| --- | --- |
| Freshness manifest | `forge-runtime.manifest.json` is an embedded file containing source identity, runtime/data/package pins and a payload-tree hash. A detached inspection copy adds the archive filename, size and digest after packing. The full file is not currently a native health field. |
| Bridge revision | HTTP `/health` exposes `revision.commit` and `revision.structuredDataManifestHash`, read from the packaged build stamp. These identify the assembly stamp and structured-data manifest; they are not the complete freshness manifest. |
| Native release evidence | The MCP `health` tool exposes `productReality.release.bundleHead` and `archiveSha256` for the archive whose reference applications were measured. A later archive may carry that ledger, so these values need not identify its containing archive. |

These distinctions are visible in `scripts/runtime/manifest.mjs`, `packages/mcp-bridge/src/health.ts`, the native health output schema and the runbook. A successful health call alone does not reverify every shipped file. An embedded manifest cannot contain its containing archive's own digest; the detached sidecar remains the archive-verification operand.

**Options and consequences.** Keep the current file plus bridge stamp and document their different purposes. Or add a bounded, versioned manifest projection to both native MCP health and bridge HTTP health. The latter improves installed-runtime inspection but changes two public output contracts and needs schema/types, missing/invalid cases, boundary tests and generated documentation. Embedding the full manifest would couple health to an expanding inspection format and could expose inert provenance that clients do not need.

**One-way-door status.** Nothing changes in m06. Once clients depend on a new health field, its name and semantics become a compatibility obligation.

**Proposed decision text, pending Derek:** “Approve a later additive nullable `releaseManifest` projection on native MCP health and bridge HTTP health. Derive it only from the containing bundle's embedded manifest, with fields `schemaVersion`, `commit`, `date`, `nodeFloor`, `thirdPartyCount`, `packageVersions`, `payloadTreeSha256`, `registrySha256`, `tokensShippedTreeSha256` and `structuredDataManifestHash`; copy source values without claiming whole-payload verification. Preserve the existing bridge `revision` and native `productReality.release` meanings. A host without an embedded manifest returns null; an invalid manifest returns null with an explicit diagnostic. Never substitute live Git HEAD, a historical release-ledger archive hash, or a fabricated containing-archive digest. Keep detached archive verification separate. Implement only after this proposal receives an explicit decision.”

The proposed field names and behavior above are a reviewable design, not an existing wire contract or authorization to edit one.

The three flattened hash names map explicitly from embedded-manifest fields: `registrySha256` from `registry.sha256`, `tokensShippedTreeSha256` from `tokensShippedTree.sha256`, and `structuredDataManifestHash` from `structuredDataManifest.sha256`. Preserve each source hash's representation as supplied. The other proposed fields retain their source names; no containing-archive digest is added.
